# 技术架构文档

## 1. 技术选型

### 1.1 整体架构

本项目采用**前后端分离架构**，分为三个主要部分：

```
┌─────────────────┐
│  微信小程序前端  │
│  (miniprogram)  │
└────────┬────────┘
         │ HTTPS/REST API
         ↓
┌─────────────────┐
│   后端服务层     │
│    (server)     │
└────────┬────────┘
         │ 调用
         ↓
┌─────────────────┐      ┌──────────┐
│   算命引擎       │      │  数据库   │
│(fortune-engine) │←────→│ MySQL/MongoDB│
└─────────────────┘      └──────────┘
```

### 1.2 技术栈选型对比

#### 前端技术选型

| 方案 | 优势 | 劣势 | 选择 |
|------|------|------|------|
| 微信原生 | 性能最优，体验最好 | 开发效率低，仅支持微信 | ✅ 采用 |
| uni-app | 跨平台，一次开发多端发布 | 性能略逊，包体积大 | 备选 |
| Taro | React语法，社区活跃 | 学习成本高 | 不采用 |

**最终选择：微信原生小程序框架 + TypeScript**

**原因：**
- MVP阶段专注微信生态
- 性能和体验最重要
- TypeScript提供类型安全

#### 后端技术选型

| 方案 | 优势 | 劣势 | 选择 |
|------|------|------|------|
| NestJS | 架构清晰，TypeScript原生支持 | 相对重量级 | ✅ 采用 |
| Express | 轻量，生态丰富 | 缺少架构约束 | 不采用 |
| Koa | 中间件机制优雅 | 需要手动集成功能 | 不采用 |

**最终选择：NestJS + TypeScript**

**原因：**
- 企业级架构，易于扩展和维护
- 原生TypeScript，与前端技术栈一致
- 依赖注入、模块化设计优秀
- 内置参数验证、异常处理等

#### 数据库选型

| 方案 | 优势 | 劣势 | 选择 |
|------|------|------|------|
| MySQL | 关系型，事务支持好 | 扩展性一般 | ✅ 主库 |
| MongoDB | 文档型，灵活性高 | 事务支持弱 | ✅ 辅助库 |
| Redis | 高性能缓存 | 非持久化 | ✅ 缓存 |

**最终选择：MySQL（主库）+ MongoDB（辅助）+ Redis（缓存）**

**数据分类：**
- MySQL：存储用户数据、订单数据、会员数据等结构化数据
- MongoDB：存储排盘记录、卦象记录等半结构化数据
- Redis：缓存排盘结果、热点数据、会话信息

- 完整的单元测试覆盖

## 3. 核心流程设计

### 3.1 八字排盘流程

```
用户输入生辰
    ↓
前端验证输入
    ↓
调用后端API
    ↓
┌────────────────┐
│ 检查Redis缓存  │
│ Key: bazi:{date}-{time}-{gender} │
└────────┬───────┘
         │
    已缓存? ──Yes──→ 返回缓存结果
         │                 │
        No                 │
         ↓                 │
┌────────────────┐         │
│ 调用算命引擎    │         │
│ fortune-engine │         │
└────────┬───────┘         │
         │                 │
         ↓                 │
  1. 公历转农历            │
  2. 计算四柱天干地支      │
  3. 计算十神              │
  4. 分析五行强弱          │
  5. 计算大运流年          │
  6. 生成命理解读          │
         │                 │
         ↓                 │
  保存到MongoDB            │
  写入Redis缓存            │
         │                 │
         ↓                 │
      返回结果 ←───────────┘
         │
         ↓
  前端展示结果
```

### 3.2 缓存策略

**三级缓存架构：**

```
L1: 小程序本地缓存（wx.storage）
    - 用户自己的排盘记录
    - 有效期：永久（除非用户清除）
    ↓
L2: Redis缓存（服务端）
    - 所有排盘计算结果
    - 有效期：7天
    - Key格式: bazi:{YYYY-MM-DD-HH}:{gender}
    ↓
L3: MongoDB持久化（服务端）
    - 用户关联的排盘记录
    - 永久存储
```

**缓存更新策略：**
- 排盘结果：写入时缓存，7天过期
- 用户信息：修改时更新缓存
- 知识库内容：CDN缓存，1天过期

## 6. 安全设计

### 6.1 认证与授权

**认证方式：**
- 微信小程序：使用 `wx.login` 获取 code，后端换取 openid
- JWT Token：用于后续请求认证
- Token有效期：7天，支持刷新

**授权流程：**
```
1. 用户打开小程序
2. 调用 wx.login 获取 code
3. 发送 code 到后端
4. 后端调用微信API获取 openid
5. 生成 JWT Token 返回
6. 小程序存储 token
7. 后续请求携带 token
```

### 6.2 数据安全

**传输安全：**
- 全站HTTPS加密
- API签名验证（可选）
- 请求频率限制

**存储安全：**
- 敏感数据加密存储（AES-256）
- 数据库密码加密
- Redis密码保护

**隐私保护：**
- 生辰信息仅用户本人可见
- 不对外公开用户排盘数据
- 支持用户删除个人数据

### 6.3 防护措施

**防刷措施：**
- IP频率限制（60次/分钟）
- 用户频率限制（20次/分钟）
- 验证码（敏感操作）

**防爬虫：**
- User-Agent检测
- Referer检测
- Token验证

**SQL注入防护：**
- 使用ORM（TypeORM）
- 参数化查询
- 输入验证

## 7. 性能优化

### 7.1 前端优化

**小程序优化：**
- 分包加载（主包 < 2MB，总包 < 20MB）
- 图片懒加载
- 使用 WebP 格式图片
- 减少 setData 调用频率
- 使用虚拟列表（长列表）

**网络优化：**
- 请求合并
- 数据缓存
- 请求去重
- 预加载关键数据

### 7.2 后端优化

**数据库优化：**
- 索引优化（生辰日期、用户ID等）
- 查询优化（避免N+1查询）
- 连接池配置
- 读写分离（未来）

**缓存优化：**
- Redis缓存热点数据
- 排盘结果缓存
- 知识库内容缓存
- CDN缓存静态资源

**算法优化：**
- 农历数据预计算（1900-2100年）
- 避免重复计算
- 批量计算优化

## 8. 监控与运维

### 8.1 日志系统

**日志分类：**
- access.log：访问日志
- error.log：错误日志
- business.log：业务日志
- slow.log：慢查询日志

**日志级别：**
- ERROR：错误信息
- WARN：警告信息
- INFO：普通信息
- DEBUG：调试信息（仅开发环境）

### 8.2 监控指标

**系统指标：**
- CPU使用率
- 内存使用率
- 磁盘IO
- 网络流量

**应用指标：**
- 请求QPS
- 响应时间（P50, P95, P99）
- 错误率
- 缓存命中率

**业务指标：**
- 排盘次数
- 活跃用户数
- 转化率

### 8.3 告警策略

**告警规则：**
- CPU > 80% 持续5分钟
- 内存 > 85% 持续5分钟

**告警渠道：**
- 企业微信
- 邮件
- 短信（紧急）
